# CONCERT RADAR — FULL BUILD SPECIFICATION

> This document is a complete specification for building Concert Radar from scratch. It contains every architectural decision, schema, service contract, file structure, and implementation detail needed to build the entire project. Execute each phase in order. Do not skip ahead. Do not add features not listed here.

---

## IDENTITY

Concert Radar is a concert discovery platform. Users follow artists (manually or via Spotify import), set a home location + travel radius, and get alerts when matching shows are announced nearby. The system scrapes ticketing platforms, resolves artists against MusicBrainz + Spotify, ranks shows using taste embeddings + geo-proximity + recency decay, and pushes notifications.

## ENGINEERING CONVENTIONS (obey these in every file)

### Python (all backend services)
- Python 3.12, FastAPI, SQLAlchemy 2.0 async, Pydantic v2, pytest
- Line length 100. Use `ruff` for linting and formatting. Use `mypy --strict` for type checking.
- Every public function gets a type signature and a one-line docstring.
- Use `uv` for dependency management. Each service has its own `pyproject.toml`.
- Use `structlog` for logging. Every log line includes `trace_id`, `span_id`, `service_name`.
- Never use `print()` in committed code. Use structured logging.
- Use `httpx` for HTTP clients (async). Never `requests`.
- Use `aiokafka` for Kafka consumers/producers.

### TypeScript / Frontend
- Next.js 14 (App Router), TypeScript strict mode, Redux Toolkit, Tailwind CSS
- No `any` types anywhere. ESLint + Prettier.
- Use `pnpm` as package manager.
- Use Drizzle ORM for database access from the Next.js API routes.
- Use Mapbox GL JS for map rendering.

### Database
- PostgreSQL 16 with PostGIS and pgvector extensions.
- Migrations are append-only SQL files in `db/migrations/`. Never edit an existing migration.
- Use `uuid` primary keys everywhere (generated by Postgres via `gen_random_uuid()`).
- All timestamps are `timestamptz`.

### Architecture rules
- Services communicate via gRPC (synchronous internal) or Kafka (asynchronous events). Never direct HTTP between backend services.
- REST is only for the gateway ↔ frontend boundary.
- Every service has `/healthz` (process alive) and `/readyz` (can serve traffic) endpoints.
- Protobuf in `proto/` is the source of truth for inter-service message contracts.
- No TODO comments in committed code. File issues instead.

### Code quality
- Prefer standard library and well-known libraries. No exotic dependencies without justification.
- If you would write a comment explaining *what* code does (not *why*), rewrite the code to be clearer instead.
- No dead code. No speculative abstractions. No premature generalization.
- Tests assert on observable behavior (DB state, HTTP response, Kafka message), never on mocks.

### 0008_functions.sql
```sql
CREATE OR REPLACE FUNCTION relevance_score(
    user_vec vector,
    artist_vec vector,
    show_date TIMESTAMPTZ
) RETURNS FLOAT AS $$
    SELECT
        CASE
            WHEN user_vec IS NULL OR artist_vec IS NULL THEN 0.5
            ELSE (1 - (user_vec <=> artist_vec)) * 0.7
                 + exp(-extract(epoch FROM (show_date - now())) / 2592000.0) * 0.3
        END
$$ LANGUAGE sql IMMUTABLE;

CREATE OR REPLACE FUNCTION update_user_taste_embedding(p_user_id UUID)
RETURNS VOID AS $$
    UPDATE users
    SET taste_embedding = (
        SELECT avg(a.embedding)
        FROM follows f
        JOIN artists a ON a.id = f.artist_id
        WHERE f.user_id = p_user_id
          AND a.embedding IS NOT NULL
    ),
    updated_at = now()
    WHERE id = p_user_id;
$$ LANGUAGE sql;
```

### 0009_views.sql
```sql
CREATE MATERIALIZED VIEW upcoming_user_feed AS
SELECT
    u.id AS user_id,
    e.id AS event_id,
    e.starts_at,
    e.title,
    e.price_min_cents,
    e.price_max_cents,
    e.status,
    e.source_url,
    e.image_url,
    v.name AS venue_name,
    v.city AS venue_city,
    ST_Distance(u.home_location, v.location) AS distance_m,
    a.id AS artist_id,
    a.name AS artist_name,
    a.image_url AS artist_image_url,
    relevance_score(u.taste_embedding, a.embedding, e.starts_at) AS score
FROM users u
CROSS JOIN LATERAL (
    SELECT e2.*
    FROM events e2
    JOIN venues v2 ON v2.id = e2.venue_id
    WHERE e2.starts_at > now()
      AND e2.status IN ('announced', 'on_sale')
      AND ST_DWithin(u.home_location, v2.location, u.travel_radius_m)
) e
JOIN venues v ON v.id = e.venue_id
JOIN event_artists ea ON ea.event_id = e.id AND ea.billing = 0
JOIN artists a ON a.id = ea.artist_id
WHERE u.home_location IS NOT NULL;

CREATE UNIQUE INDEX idx_upcoming_feed_user_event ON upcoming_user_feed (user_id, event_id);
CREATE INDEX idx_upcoming_feed_score ON upcoming_user_feed (user_id, score DESC);
```

## SERVICE SPECIFICATIONS

### Gateway (services/gateway/)

FastAPI application. This is the only service the frontend talks to.

**Endpoints:**

```
POST   /auth/spotify          — initiate Spotify OAuth, return redirect URL
GET    /auth/spotify/callback — handle OAuth callback, create/update user, return JWT
GET    /me                    — return current user profile
PATCH  /me                    — update home_location, travel_radius_m, alert prefs
GET    /artists/search?q=     — trigram search on artists table, return top 10
POST   /follows               — body: {artist_id}. Insert follow, recompute taste embedding, publish users.taste_updated to Kafka
DELETE /follows/:artist_id    — remove follow, recompute taste embedding, publish users.taste_updated
GET    /feed?cursor=&limit=   — paginated query on upcoming_user_feed materialized view, sorted by score DESC
GET    /events/:id            — event details with all artists, venue info
POST   /events/:id/dismiss    — insert dismissal, excluded from future feed queries
WS     /ws/feed               — WebSocket that pushes new matches in real time
```

**Auth:** JWT tokens. For v1, skip OAuth complexity — use a simple `/auth/dev` endpoint that takes an email and returns a JWT for development. Wire up real Spotify OAuth as a separate PR.

**Dependencies:** `fastapi`, `uvicorn`, `sqlalchemy[asyncio]`, `asyncpg`, `pydantic-settings`, `python-jose[cryptography]`, `aiokafka`, `httpx`, `structlog`, `opentelemetry-*`.

### Scraper — Ticketmaster (services/scraper-ticketmaster/)

CLI tool that runs on a schedule (k8s CronJob or `make dev-scraper`).

**Behavior:**
1. Call Ticketmaster Discovery API `/events.json` with `classificationName=music` and `dmaId=249` (default, configurable)
2. Paginate through all results (max 200 per page, up to 5 pages)
3. For each event: parse into internal schema, upsert venue (match on `source_ids.ticketmaster`), upsert event (match on `source=ticketmaster, external_id`)
4. For events already in DB: detect status changes, publish `events.status_changed`
5. For new events: publish `events.discovered`

**Config:** `TICKETMASTER_API_KEY`, `DMA_ID`, `KAFKA_BOOTSTRAP_SERVERS`, `DATABASE_URL`.

### Enricher (services/enricher/)

Long-running Kafka consumer.

**Behavior:**
1. Consume `events.discovered`
2. For each artist name in the event:
   a. Search MusicBrainz by name (1 req/sec rate limit). Accept top result if score > 70.
   b. If MB match found and artist not in DB: look up Spotify metadata by MB ID or name search.
   c. Compute embedding: pass the joined genre string (e.g. "indie rock, shoegaze, dream pop") through `sentence-transformers/all-MiniLM-L6-v2` to get a 384-dim vector.
   d. Upsert artist with `ON CONFLICT (mbid) DO UPDATE`.
3. Link artists to event in `event_artists`
4. Publish `events.enriched`

**Idempotency:** Same message consumed twice must not create duplicates. Use upserts everywhere.

### Matcher (services/matcher/)

Long-running Kafka consumer.

**Behavior:**
1. Consume `events.enriched` — find all users within range of the event's venue, compute relevance_score, publish `matches.proposed` for scores above threshold (0.3 default)
2. Consume `users.taste_updated` — re-run matching for this user against all upcoming events in their radius
3. Periodically trigger `REFRESH MATERIALIZED VIEW CONCURRENTLY upcoming_user_feed`

### Notifier (services/notifier/)

Long-running Kafka consumer.

**Behavior:**
1. Consume `matches.proposed`
2. Check `alerts_sent` — skip if already notified for this (user, event, channel)
3. Check user preferences (alert_email, quiet_hours)
4. Send email via AWS SES (or log to console in dev mode)
5. Record in `alerts_sent`
6. Publish `notifications.sent`

### Recommender (services/recommender/)

gRPC server.

**Behavior:**
1. Accept `GetRecommendations(user_id, limit)` RPC
2. Query upcoming events NOT already in user's feed/dismissals
3. Rank by pgvector similarity between user taste_embedding and artist embedding
4. Diversify: no more than 2 events from the same genre cluster in top 10
5. Return ranked list

### Pages

1. **Feed page** (`/`) — infinite-scroll list of upcoming events ranked by score. Each card shows: artist name, venue, date, distance, price range, follow/dismiss buttons. Filter drawer slides from right.
2. **Map page** (`/map`) — Mapbox GL map with clustered event pins. Click pin → event detail card. Filter drawer same as feed.
3. **Artist page** (`/artist/[id]`) — artist info, upcoming shows, "fans also follow" via pgvector.
4. **Event page** (`/event/[id]`) — full event detail, lineup, venue map, ticket link.

## CRITICAL REMINDERS

1. **Build phases sequentially. Do not skip ahead.** Phase 2 depends on Phase 1. Phase 4 depends on Phase 3. Breaking this order creates integration bugs that waste hours.
2. **Each phase should result in a working, testable state.** If phase 3 is done, the app works with direct DB access. If phase 4 is done, it works with Kafka.
3. **Write tests for every service.** Integration tests using testcontainers for Postgres and Redpanda. Unit tests for parsing, ranking, dedup logic.
4. **Every Kafka consumer must be idempotent.** Processing the same message twice must produce the same result.
5. **Do not over-engineer.** No plugin systems, no factory patterns, no AbstractBaseService classes. Direct, readable code.
6. **Commit after each sub-step.** Small commits, clear messages.
